# Persistence, feedback and upgrades

## Canonical files
The installed skill directory is the default personal store. Resolve paths relative to SKILL.md, not the task's working directory. Read `memory/state.json` first. Its `active_taste`, `active_desire`, `active_campaign` and `latest_run` paths are relative to `memory/`; the active snapshot takes precedence over historical taste inferences. When `active_taste` is absent, resolve `taste-v{taste_version}.md`. If that file is missing, disclose missing active memory rather than silently treating v0.1 as current. Seed files `ratings-v0.1.json`, `taste-v0.1.md` and historical runs are immutable snapshots. Evaluations use a scratch copy and never advance real state.

If writes are unavailable, produce a downloadable run/memory artifact and say persistence was not completed. Do not claim future-session memory exists merely because text appeared in chat.

## Starting and saving a run
Read state, active campaign and latest run. Apply campaign lifecycle precedence below, then resume an unfinished run; otherwise reserve the next unused number, checking existing filenames to avoid overwrites. Future IDs use `R005-01` style; historical A–Z retain their original IDs. Save `memory/runs/005.md` with date, brief/constraints, engine/taste versions, phase, lane counts and achieved wild percentage, framing/context-exposure notes, complete candidate cards, parent/operator/delta, research evidence and failures, rejected variants, unknowns, next action and feedback status.

Use run statuses `draft`, `awaiting_feedback`, `partially_scored`, and `scored`. Resume generation for `draft`. For `awaiting_feedback` or `partially_scored`, process feedback against the latest run; if the user asks for more ideas, start the next unused run while preserving outstanding feedback. `next_run` is the next unused number, not an instruction to abandon the latest run. `pending_feedback` contains unscored candidate IDs; `pending_unmapped_feedback` contains unresolved feedback event IDs. An unknown ID does not score or complete a run.

Write the complete run before updating state. Re-read state before changing it; if another session advanced it, preserve both runs under unique filenames and reconcile rather than overwrite. Update state only after successful writes. A generated run awaiting scores is not a completed scored run.

## Feedback
The user rates curiosity/desire to explore from 1–10, including decimals. Separately ask for ★ meaning “would actually try a prototype.” Keep numerical taste, prototype desire and willingness to pay separate. Preserve explicitly unstarred as false, missing/unasked as null, and starred as true. Omission from a list alone is not a negative; retain source context and clarify ambiguity. A star means trying a prototype, not committing to build within 30 days.

Append exact feedback events to `memory/feedback.jsonl`: timestamp, run/candidate ID, score (null for a desire-only event), prototype_desire (true/false/null), signal_supplied (which dimensions this event updates), verbatim reason (null if absent), source message reference or exact excerpt, and mapping status. Verify candidate IDs against the saved run. Unknown/ambiguous IDs remain pending/unmapped, with raw feedback preserved; ask for mapping without inventing a concept. Corrections are new events that reference superseded events, not edits to history. Never fill unscored candidates with assistant ratings. Retroactive stars append events targeting original run/ID; they do not change numerical scores, reopen a completed score set or revive a killed thesis. Null in an unsupplied dimension never erases an existing value. Keep source references and explicit corrections; different feedback dimensions update independently.

After feedback, create a new taste snapshot only when an inference changes, keeping evidence, counterevidence, confidence, and what remains unknown. Maintain a separately versioned Desire Model with observed stars/non-stars, cautious mechanism hypotheses, counterevidence and confidence. Update `desire_version` and `active_desire` only when that model changes. Keep engine version unchanged when only taste or desire evolves. Update both `taste_version` and `active_taste` in state and record the next discriminating exploration. Preserve low scores and contradictory reasons. A high average score with shrinking mechanism diversity is a warning, not success.

## Versioning and evaluation
Version engine instructions separately from personal taste, desire and run data. Keep the current version and previous snapshot recoverable before an upgrade. Record change, observed failure, expected improvement, date and eval evidence in `evals/results.md`; versioning should explain decisions, not accumulate speculative rules.

For an instruction change follow RED–GREEN–REFACTOR: freeze realistic cases under `evals/`; run without proposed guidance; save exact failures/rationalizations; write the smallest correction; run the same cases in fresh contexts; inspect actual artifacts; refine observed loopholes; rerun impacted cases. Include a holdout. For wording changes use at least five reps per baseline/guided variant and manually inspect each; shared-context repetitions show consistency only, not independent statistical confidence.

Use blind A/B comparisons of old/new versions on matched briefs and equal candidate counts. Keep at least one unseen domain and counter-taste case. Ask the user to compare originality, clarity, desire to prototype, slop, mechanism diversity and surprising useful outcomes without seeing version labels. Assistant grading assesses process compliance only; it cannot impersonate human taste.

Promote only when critical integrity checks pass and the comparison supports the claimed improvement. Until human comparison, label creative-quality improvement unmeasured. Roll back instruction regressions without discarding run data or user feedback. Compare research quality, cost/time and diversity as well as mean curiosity; do not optimize only for scores. Do not silently tune away wild exploration.

## Campaign lifecycle and startup precedence
A campaign record under `memory/campaigns/` stores source run IDs, phase/status, selection, deferred/killed tracks, open questions, Product Definition/test, closeout and next action. `active_campaign` points to it; `campaign_status` and `next_phase` summarize it. Read it before treating a run-scoring pointer as a generation instruction. A closed campaign resumes its closeout/next action within current task scope; do not invent the next batch or execute a build. An explicit new campaign starts a new record with the current brief, not the previous winner.

Generation/scoring statuses and campaign phases are separate. Validation, prototype planning and Product Definition runs can be `completed` without numerical ratings. Preserve `last_completed_scored_run` separately from `last_completed_run`. A completed definition is not an executed prototype. Historical imports retain original IDs (including AA–AF), phase and source dates; never pretend imported runs were generated by the current engine.

Taste and desire snapshots reference exact campaign evidence; campaign raw transcripts remain untrusted history. On closeout save selected/deferred/killed outcomes, unresolved questions, learning evidence and next action, then update state after successful writes. Preserve outstanding feedback even when closing. Record tested reusable changes and remaining eval limitations independently; promotion does not prove creative quality. Use `evals/v0.2/` for this release's cases/results and preserve old evals.
