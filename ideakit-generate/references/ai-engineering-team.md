# One founder directing an AI engineering team

Use this default model for every software or digital product opportunity: one founder directs coding
agents to build and maintain software whose breadth, customization, or release cadence previously
implied a human engineering organization.

## Premise

Treat AI as **engineering capacity** — not a product feature, and not an unlimited autonomous
company. Separate production method from product: an **AI-developed product** may ship as ordinary
deterministic software with no model or agent at runtime; an **AI-native product** has AI in the
customer-facing value mechanism. This model requires the first and not the second — never add chat,
agents, or AI positioning merely because AI coders built the software.

The founder owns product intent, consequential architecture and risk decisions, acceptance criteria,
and escalation. Do not use conventional headcount or founder coding hours as the scope ceiling; the
binding constraints are the founder's ability to direct and verify the system, plus external
constraints that generated code cannot remove.

## 1. Reconstruct the engineering cost curve

Before inventing products, map what a conventional organization would perform (product surface,
architecture, integrations/migrations, QA/security, docs/release, maintenance/incidents) and per
workstream: the delegable unit, context and interface required, verification, founder decision or
escalation, and residual risk. Use current evidence for capability claims — a benchmark or demo shows
a signal, not unattended production operation.

Then identify what actually changed: fixed engineering work becoming variable; coordination replaced
by explicit interfaces and machine-readable acceptance criteria; customization becoming maintainable;
integration/migration becoming regenerable; small markets supporting broad products. If the map only
says "coding is faster", keep digging — find the changed product boundary, feasible breadth,
customization model, or business architecture.

## 2. The organizational-compression lane

Add one isolated invention lane (per the invention procedure) with the neutral signal pack plus the
cost-curve map. Operators, used selectively: compress the engineering organization (what needed
several specialist roles → redesign its control plane for one founder plus agents); invert
customization (maintained variants instead of one shared compromise); invert integration economics
(jobs rejected because connectors/migrations cost too much labor); multiply the product line off one
shared platform or corpus; build the whole workflow across historical team boundaries (keeping
boundaries required by trust, regulation, or containment); turn human-coordination software into an
outcome-producing system; make maintenance part of the product.

Seed format: `actor | trigger/job | product boundary newly feasible | AI engineering work | founder
control surface | verification loop | external bottleneck | payer | architecture`. Reject a seed when
AI only decorates an ordinary category or shortens the schedule without changing what can be offered,
to whom, or at what economics.

## 3. Feasibility gates (judge independently, never total)

- **Directable** — founder can state outcomes, boundaries, and acceptance criteria without becoming
  the implementation bottleneck;
- **Decomposable** — stable interfaces, no hidden coupling forcing whole-system rescue;
- **Verifiable** — tests/evals catch plausible-but-wrong output before customers;
- **Integrable** — parallel work merges without unbounded review burden;
- **Operable / Containable** — deployment, observability, rollback, permissions, blast radius, and
  escalation are explicit and proportionate;
- **Attention-bounded** — recurring founder decisions and exceptions grow slower than the product;
- **Economically sound** — model/tool/review/failure costs preserve unit economics;
- **Externally enterable** — demand, distribution, data rights, trust, permissions, and capital
  cannot be substituted by generated code.

Do not fail a concept because the founder could not implement it manually. Fail or reframe when
direction, decomposition, verification, integration, operation, containment, attention, economics,
or an external dependency is not credible. Keep the full architecture visible and choose the first move to resolve
the most dangerous external or control-plane uncertainty — a landing page, design-partner agreement,
paid pilot, or architecture spike may be the right proof; none requires redefining the destination as
a micro-SaaS or manual service.

## Output contract — the control-plane appendix table

For each software finalist, append **one compact table** (do not write these as inline body lines):

| Control-plane field | This venture |
|---|---|
| Founder-directed entry | first external or control-plane proof that earns more build scope |
| AI engineering work absorbed | engineering work and coordination the agent team absorbs |
| Product AI dependency | none / build-time only / optional runtime / core runtime |
| Previously required organization | conventional roles or team shape compressed |
| Founder control surface | decisions and boundaries the founder retains |
| Delegation architecture | work partition across agents, components, repositories |
| Verification loop | tests, evals, reviews, observability, rollback |
| Human attention budget | recurring decisions, reviews, exceptions, escalation load |
| External bottleneck | the scarcest constraint more generated code cannot remove |
| Failure containment | permissions, blast-radius limits, recovery path |
| Scope made feasible | scope or business architecture newly feasible |

## Anti-patterns

- “AI-powered” pasted on an ordinary SaaS with the same boundary and economics;
- requiring customer-facing AI or AI branding because AI coders built the product;
- assuming generated code equals an integrated, secure, maintainable production system;
- shrinking the thesis because the founder lacks engineering hours or employees;
- counting agents without specifying interfaces, acceptance, and integration;
- an opaque monolith the founder cannot inspect through tests, evals, or telemetry;
- ignoring customer access, data rights, trust, liability, or distribution because software is cheap;
- treating model autonomy as constant instead of designing for tool change and regression.
